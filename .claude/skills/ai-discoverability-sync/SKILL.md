# AI Discoverability Sync

RidgeHQ intentionally states product facts in seven places so AI assistants and search
engines can find and verify them independently. When one changes, the other six drift
unless checked deliberately. This skill runs that check every time.

## When to use this

Trigger on any of:
- A vertical, product, or platform capability's copy, status, or feature list changes
  in `src/lib/config/verticals.ts`, `products.ts`, or `platform.ts`.
- Pricing mode/commission/phase changes in `src/lib/config/marketing.ts`.
- An integration's `state` changes in `src/lib/config/integrations.ts`.
- A new page, tool, or blog post is added or removed.
- A capability claim (especially AI Copilot behavior) is added, reworded, or reviewed.
- You're asked to "sync with the vault" / "check for vault updates" — see "Vault ↔ website
  sync" below.

Do **not** use this for pure visual/layout changes that touch no factual copy.

## The 7 surfaces

1. **`src/lib/config/product-knowledge.ts`** — the canonical knowledge model. Most
   fields are derived automatically from `verticals.ts`/`products.ts`/`platform.ts`/
   `integrations.ts`/`marketing.ts`/`faq.ts` via `.map()`, so a source-file change often
   propagates for free — confirm the shape still matches (no renamed/removed fields the
   mapping relies on). The hand-written fields (`positioning`, `idealCustomerProfile`,
   `poorFitCustomerProfile`, `security.summary`) do **not** auto-update — re-check them
   by hand against the change.
2. **`public/llms.txt`** — hand-written. Update the relevant section (Products,
   Industries, Platform, Company, Free calculators, Machine-readable summary) to match.
   Never state a specific price here while `marketingConfig.pricingMode === 'pilot'`.
3. **`src/app/ai/page.tsx`** — reads `productKnowledge` directly, so if step 1 is
   correct this page updates for free. Re-run `next build` and spot check the route
   renders the new fact.
4. **FAQPage JSON-LD sources** — `src/lib/config/faq.ts` (`generalFaqs`, rendered on
   `/`), plus each vertical's/product's/capability's own `faqs[]` array (rendered on
   `/solutions/[slug]`, `/products/[slug]`, `/platform/[slug]`). If the change affects
   a question users would plausibly ask about it, add or correct the FAQ entry — don't
   let `/ai` or `llms.txt` state something the page's own FAQ doesn't corroborate.
5. **`src/app/sitemap.ts`** — most routes are generated by mapping over `verticals`/
   `products`/`platformCapabilities`/`blogPosts`, so a new entry in those config arrays
   is picked up automatically. A genuinely new static route (like `/tools/*` or `/ai`)
   must be added to the `staticRoutes` array by hand.
6. **Page metadata** — every page's `metadata`/`generateMetadata` (built via
   `pageSeo()` from `src/lib/config/seo.ts`) should still accurately describe the page
   after the change. Rewrite thin/generic descriptions into problem+audience+relevance
   form; never leave a description that now contradicts the page body.
7. **Marketing/nav copy** — `src/lib/config/navigation.ts` menu descriptions, and the
   relevant `verticals.ts`/`products.ts`/`platform.ts` prose (hero copy, feature
   sections, FAQs). For anything that is a **capability claim** (what the product does,
   not just how it's phrased), verify it against the authoritative Brain vault at
   `D:\work\RidgeHQAPP\Brain\RidgeHQAPP\wiki` before publishing — see
   "Product-truth verification" below. Pure copy/tone edits don't need this step.

## Procedure

1. Identify what fact changed and which source-of-truth file it lives in
   (`verticals.ts`, `products.ts`, `platform.ts`, `integrations.ts`, or `marketing.ts`).
2. Walk the 7 surfaces above in order. For each: read the current content, decide
   in-sync / needs-update / not-applicable, and note it — don't skip a surface just
   because it seems unlikely to be affected.
3. Apply the needed edits. Keep them surgical — don't rewrite copy the change didn't
   touch.
4. If the change is or touches a capability claim, do the product-truth verification
   pass below before finalizing wording.
5. Verify: `npx tsc --noEmit`, `npx eslint <changed files>`, `npx next build`. Confirm
   the new/changed fact actually appears in the relevant built HTML
   (`.next/server/app/**`) where that matters (e.g. `grep` the built `/ai` page or the
   relevant `/solutions/[slug]` output).
6. Commit with a message naming which of the 7 surfaces were touched and which were
   confirmed already in sync.

## Product-truth verification

For any change that is or touches a capability claim (not just copy polish):

1. Check `RidgeHQ_Website_AI_Prompt/01-SOURCE-OF-TRUTH.md` for the current reading
   order and any explicit overriding decisions.
2. Read the relevant doc(s) under
   `D:\work\RidgeHQAPP\Brain\RidgeHQAPP\wiki\development-reference\Modules\`
   (or `APIs/`, `Architecture/`, or the newest QA/decision doc under `Docs/`) for the
   feature in question. Prefer the newest, most specific implementation doc over a
   broad business summary.
3. Never publish a claim the Brain vault doesn't support, and never generalize a
   partial/scoped capability into an unqualified one (the AI Copilot's undo coverage —
   5 of ~41 tools, financial/booking actions excluded — is the running example: state
   it scoped, the way `src/lib/config/products.ts`'s AI Copilot FAQ already does,
   never as a blanket "every action is reversible").
4. If the Brain vault is unreachable or silent on the specific claim, don't publish it
   as current — mark it planned/unverified or leave it out, per AGENTS.md's product-
   truth rule.

## Vault ↔ website sync (pull + push)

The Brain vault is the app/business source of truth; this repo is downstream. Run this
whenever asked to "sync with the vault," and periodically (e.g. before a marketing content
push) even without being asked:

**Pull — vault changed, website may be behind:**
1. Open `docs/vault-sync-log.md` and note the date of its last entry.
2. Read `wiki/index.md`'s dated `## <topic> update - <date>` sections and `wiki/log.md`
   entries newer than that date. `index.md` is the faster read — it summarizes each ingest;
   drop into `log.md` or the specific page (`pricing.md`, `business-context.md`,
   `competitors.md`, etc.) for detail.
3. For each change found, decide: does it affect any of the 7 surfaces? If yes, is it
   **safe to apply directly** (a copy-accuracy fix, a status correction that doesn't change
   what's sold or for how much) or **consequential** (pricing, a positioning pivot, a claim
   that commits the business to something)? Apply the safe ones following the normal 7-
   surface procedure above. For consequential ones: do not publish unprompted — surface it
   clearly and get a go-ahead first.
4. Append a dated entry to `docs/vault-sync-log.md` either way (what was pulled, what was
   applied, what's flagged and pending), so the next pass knows where it left off.

**Push — website work surfaced something the app/business side should know:**
1. Never edit the vault's own pages directly (`business-context.md`, `pricing.md`,
   `competitors.md`, etc.) — those are owned and maintained by whatever session works in
   that repo.
2. Append an entry to `wiki/log.md` in the vault, matching its existing format exactly:
   `## [YYYY-MM-DD] query | <title>`, then a short `Source:` line, then the finding in
   prose. Use `query` (not `ingest`) since a website-repo session isn't ingesting a new
   source into that vault, just reporting back.
3. Mirror the same finding in `docs/vault-sync-log.md` on this side, so both logs tell the
   same story from their own vantage point.

## Non-goals

- This skill does not invent new facts, pricing, testimonials, or integrations — it
  only propagates a fact that already changed in a source config file, or corrects a
  surface that contradicts the Brain vault.
- This skill does not decide *whether* to make a product/marketing change — only that,
  once made, it's reflected everywhere it needs to be.
